# 파운데이션 모델 — 모달리티와 과제의 벽이 무너지다

## 한눈에 보기
| 항목 | 핵심 |
|------|------|
| 무너진 벽 1 | 데이터 형식 — 글만/이미지만/소리만 다루던 분야 구분이 사라짐 |
| 무너진 벽 2 | 과제 — 한 과제 전용 모델에서 범용 모델로 |
| "토대"라는 이름 | 중요하다는 뜻 + 그 위에 얹어 지을 수 있다는 뜻, 둘 다 |
| 대가 | 범용은 기본은 하지만 특정 과제에서 최고는 아니다 → 적응이 필요해진다 |
| 이 책에서의 용법 | LLM과 LMM을 함께 가리키는 말 |

## 1. 왜 이게 필요한가

### 이런 상황을 상상해 보자
어떤 회사에 모델이 세 개 있다.

```text
스팸 분류 모델    ← 글만 먹는다.      번역? 못 한다.
이미지 분류 모델  ← 사진만 먹는다.    사진 속 글자를 읽어달라? 못 한다.
음성 인식 모델    ← 소리만 먹는다.    이 목소리가 화났는지 판단? 못 한다.
```

이건 이 회사의 게으름이 아니라 오랫동안 AI 연구가 조직되어 온 방식 자체였다.
자연어 처리(NLP)는 글만, 컴퓨터 비전은 이미지만, 음성 처리는 소리만 다뤘다.
분야가 데이터 형식(모달리티)을 따라 갈라져 있었고, 모델도 그 경계 안에서 만들어졌다.

### 여기서 뭐가 무너지나
두 가지가 동시에 걸린다.

**첫째, 세상은 한 가지 형식으로 오지 않는다.** 사람은 언어만으로 세상을 인식하지 않는다.
보고, 듣고, 만진다. 글만 읽을 수 있는 AI는 현실 세계에서 할 수 있는 일이 반쪽이다.

**둘째, 과제마다 모델을 새로 만들어야 한다.** 감성 분석 모델은 번역을 못 하고, 번역 모델은 감성 분석을
못 한다. 새 과제가 생길 때마다 데이터를 모으고 모델을 처음부터 학습시켜야 한다 —
100만 개 예시와 6개월짜리 작업이다.

### 그래서 나온 생각
언어 모델에 다른 형식의 데이터를 **함께 먹인다**. 두 종류 이상의 데이터 형식을 다루는 모델이
**[[멀티모달-모델]]**(= 글·이미지·소리 등 두 가지 이상의 데이터 형식을 다루는 모델)이고,
그중 생성까지 하는 것을 **[[LMM]]**(= 생성형 멀티모달 모델. LLM의 멀티모달 판)이라 부른다.

언어 모델이 "지금까지의 글 토큰"을 조건으로 다음 토큰을 냈다면, 멀티모달 모델은
"지금까지의 글 토큰 **+ 이미지 토큰**"을 조건으로 다음 토큰을 낸다. 구조를 바꾼 게 아니라
조건에 넣는 것을 늘렸다.

그런데 이렇게 만들어진 모델은 형식만 넓어진 게 아니라 **할 수 있는 과제도 넓어졌다.**
규모와 학습 방식 덕분에 하나의 모델이 감성 분석도 하고 번역도 한다.
그래서 이런 모델을 LLM이라 부르는 것으로는 부족해졌다 — 그 이름이 **[[파운데이션-모델]]**
(= 여러 데이터 형식을 다루고 넓은 범위의 과제를 두루 해내는 대형 모델)이다.

**"토대(foundation)"라는 이름은 두 가지를 동시에 말한다.** 하나는 이 모델들이 AI 응용에서 갖는
중요성이고, 다른 하나는 **그 위에 각자의 필요에 맞춰 얹어 지을 수 있다**는 것이다.
후자가 이 책 전체의 주제다 — 이 책은 그 "얹어 짓는 법"에 관한 책이다.

## 2. 어떻게 동작하는가

**1단계 — 여러 형식을 같은 자리에 놓는다.**
글과 이미지를 한 모델이 다루려면 둘을 비교 가능한 형태로 바꿔야 한다. 그 형태가
**[[임베딩]]**(= 데이터의 의미를 담아내려고 만든 숫자 벡터)이다 — 형식이 달라도 숫자 벡터로 바꿔 놓으면
"이 사진과 이 문장이 같은 것을 가리킨다"를 거리로 잴 수 있기 때문이다.

**2단계 — 라벨 없이 (이미지, 글) 쌍을 모은다.**
멀티모달 모델도 규모를 키우려면 데이터가 필요하고, 여기서도 라벨링 비용이 병목이다.
OpenAI는 CLIP을 학습시킬 때 사람에게 이미지 설명을 새로 쓰게 하지 않았다. 대신 **인터넷에서 이미
나란히 붙어 있던 (이미지, 설명글) 쌍**을 그대로 긁어왔다 — 이 방식이
**[[자연어-지도]]**(= 인터넷에 이미 함께 있던 이미지–설명글 쌍을 학습 신호로 쓰는 방식)다.
이렇게 모은 게 4억 쌍, ImageNet의 400배다. 사람 손이 들어가지 않았기 때문에 가능한 규모다.

**3단계 — 그 위에 생성 모델을 올린다.**
CLIP 자체는 생성 모델이 아니다. 열린 출력을 만들도록 학습된 게 아니라 글과 이미지의 공통 임베딩을
만들도록 학습됐다 — 이 구분이 중요하다. Flamingo·LLaVA·Gemini 같은 생성형 멀티모달 모델은
이런 멀티모달 임베딩 모델을 **뼈대로 삼아** 그 위에 세워진다.

**4단계 — 범용 모델을 특정 용도로 좁힌다.**
범용 모델은 상자에서 꺼내자마자 많은 과제를 웬만큼 해낸다. 그런데 "웬만큼"이 문제다.

소매업체 웹사이트에 올릴 상품 설명을 생성한다고 하자. 기본 모델은 사실관계가 맞는 설명을 써주지만,
그 브랜드 특유의 목소리를 못 잡고 강조해야 할 메시지를 놓친다. 마케팅 상투어로 가득한 글이 나오기도 한다.
이걸 좁히는 방법이 세 가지 있고, 이 책의 나머지가 전부 이 셋에 관한 것이다 —
지시와 예시를 정교하게 쓰는 것, 외부 데이터베이스를 붙여주는 것, 모델 자체를 더 학습시키는 것.

## 3. 그림으로 보기

```text
[예전 — 모달리티가 분야를 갈랐다]

  NLP        │  Computer Vision  │  Speech
  글만       │  이미지만         │  소리만
  ───────────┼───────────────────┼──────────────
  번역       │  객체 탐지        │  음성 인식(STT)
  스팸 탐지  │  이미지 분류      │  음성 합성(TTS)

  ▶ 벽이 두 겹이다. 가로 벽(모달리티)과, 칸 안에서 과제마다 다시 갈라지는 세로 벽.
    감성 분석 모델은 같은 NLP 칸의 번역조차 못 한다.


[지금 — 파운데이션 모델]

              글 토큰  +  이미지 토큰  ( + 소리, 영상, 3D, 단백질 구조 … )
                    │         │
                    └────┬────┘
                         ▼
                 ┌───────────────┐
                 │ 파운데이션 모델 │  ← 하나의 토대
                 └───────┬───────┘
                         │  기본은 다 하지만, 어느 것도 최고는 아니다
          ┌──────────────┼──────────────┐
          ▼              ▼              ▼
     프롬프트         RAG           파인튜닝      ← 내 용도로 좁히는 3가지 (= 모델 적응)
     엔지니어링    (DB 붙이기)   (가중치 바꾸기)
          │              │              │
          ▼              ▼              ▼
       내 응용         내 응용        내 응용     ← 토대 위에 얹어 짓는 것들
```

| 축 | 전용 모델 (task-specific) | 파운데이션 모델 |
|---|---|---|
| 다루는 과제 수 | 하나 | 다수 |
| 새 과제 대응 | 처음부터 다시 학습 | 적응(프롬프트·RAG·파인튜닝) |
| 필요한 데이터 | 100만 예시 · 6개월 | 10 예시 · 주말 하나 |
| 모델 크기 | 작다 → 빠르고 싸다 | 크다 → 느리고 비싸다 |
| 특정 과제 최고 성능 | 유리할 수 있음 | 기본은 하지만 최고는 아님 |

## 5. 자주 헷갈리는 것
- **멀티모달 = 생성형? 아니다.** CLIP은 멀티모달이지만 생성 모델이 아니다. 임베딩을 만들 뿐이다.
  구분 테스트: "이 모델이 열린 출력을 만들어내는가?" CLIP은 아니오, Gemini는 예.
- **LLM vs 파운데이션 모델** — Gemini나 GPT-4V를 아직도 LLM이라 부르는 사람이 많지만,
  글 말고도 다루므로 파운데이션 모델이라 부르는 쪽이 정확하다. 이 책은 LLM과 [[LMM]]을 아울러
  파운데이션 모델이라 쓴다.
- **범용 ≠ 항상 우월** — 전용 모델이 더 작아서 더 빠르고 싼 경우가 많다. 범용의 장점은 성능이 아니라
  **새 과제에 붙는 속도**다.

## 6. 언제 안 쓰나 / 경계
- **전용 모델이 나은 경우가 여전히 있다.** 과제가 고정돼 있고 지연·비용이 빡빡하면 작은 전용 모델이
  유리하다. 이건 결국 만들 것이냐 살 것이냐(buy-or-build)의 고전적 판단이다.
- **상자에서 꺼낸 그대로는 브랜드·도메인 요구를 못 맞춘다.** 사실관계는 맞아도 목소리가 틀린다.
  그래서 파운데이션 모델은 "쓰면 끝"이 아니라 반드시 적응 단계를 동반한다.
- **토대가 자라면 내가 올린 층이 삼켜질 수 있다.** 토대 위에 짓는다는 비유는 여기서 깨진다 —
  진짜 건물 토대는 다 지으면 형태가 고정되지만, 파운데이션 모델은 계속 커진다.
  모델이 PDF 파싱을 못 한다는 가정 위에 PDF 파싱 앱을 지었다면, 그 가정이 깨지는 날 앱도 같이 깨진다.

## 7. 연결
- [[language-model]] — 파운데이션 모델은 언어 모델의 조건부에 다른 형식의 토큰을 더한 것이다. 구조가 아니라 조건이 늘었다.
- [[self-supervision]] — 자연어 지도는 자기지도학습의 멀티모달 판이다. 라벨링 병목을 피하는 같은 수법이 형식만 바꿔 반복된다.
- [[ai-engineering]] — "토대 위에 얹어 짓는다"는 그 행위 자체에 붙은 이름이 AI 엔지니어링이다.
- [[planning-ai-applications]] — 토대가 계속 자란다는 성질이 곧 제품 방어가능성 문제로 이어진다.

## 8. 스스로 확인
1. 파운데이션 모델이 무너뜨린 벽은 두 종류다. 각각 무엇이고, 어느 쪽이 더 근본적인 변화인가?
2. CLIP은 멀티모달인데 왜 생성 모델이 아닌가? 그런데도 왜 생성형 멀티모달 모델의 뼈대가 되는가?
3. 자연어 지도가 4억 쌍을 모을 수 있었던 이유를, ImageNet의 5센트짜리 라벨링과 대비해 설명하라.
4. 범용 모델을 쓰는데도 왜 적응이 반드시 필요한가? 상품 설명 예시로 답해 보라.
