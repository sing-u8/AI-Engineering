# 01. 머신러닝 엔지니어링 vs AI 엔지니어링

## 📌 핵심 요약 & 전체 맥락
> **"모델을 학습시킬 데이터를 모으느라 6개월을 허비하지 마라. GPT API로 내일 당장 프로토타입을 만들어라."**  
> 
> 기존의 머신러닝(ML) 엔지니어링과 새롭게 부상한 **AI 엔지니어링**은 출발점 자체가 다릅니다. ML 엔지니어링이 데이터를 수집하고 정제하여 모델을 학습시키는 **데이터 중심(Data-first)**의 패러다임이었다면, AI 엔지니어링은 이미 완성된 거대 파운데이션 모델(Foundation Models)을 활용해 즉각적으로 비즈니스 가치를 창출하는 **제품 중심(Product-first)**의 패러다임입니다.

---

## 1. 패러다임의 전환: ML에서 AI로

과거에는 딥러닝 애플리케이션을 하나 만들기 위해 엄청난 초기 자본과 시간이 필요했습니다.
하지만 OpenAI의 GPT, Meta의 Llama 등 초거대 파운데이션 모델이 API나 오픈소스로 제공되면서 진입 장벽이 완전히 붕괴되었습니다.

| 구분 | 전통적 머신러닝 (ML Engineering) | 최신 AI 엔지니어링 (AI Engineering) |
| :--- | :--- | :--- |
| **시작점** | 방대한 데이터 수집과 라벨링 | 비즈니스 문제 정의 및 프롬프트 작성 |
| **핵심 업무** | 아키텍처 설계, 가중치 학습(Training), 하이퍼파라미터 튜닝 | 파운데이션 모델 연동, RAG 설계, 프롬프트 최적화, Guardrails 구축 |
| **초기 투자 시간** | 수개월 ~ 수년 (데이터 수집 및 학습 시간) | 수일 ~ 수주 (API 연동 및 프로토타이핑) |
| **지식 요구사항** | 선형대수학, 미적분, PyTorch 밑바닥 구현 지식 | 시스템 아키텍처 설계, API 통합, 평가(Eval) 지표 설계 |

---

## 2. "Data-First"의 함정과 "Product-First" 마인드셋

### ⚠️ Data-First의 3가지 함정
많은 전통적 데이터 팀들이 범하는 가장 큰 실수는 **"데이터가 모일 때까지 제품 출시를 미루는 것"**입니다.
1. **비용 낭비:** 라벨링과 데이터 클렌징에 막대한 인건비와 시간이 소모됩니다.
2. **시장 적합성(PMF) 검증 지연:** 데이터를 모아 6개월 뒤에 모델을 완성했지만, 정작 고객이 원하지 않는 기능일 수 있습니다.
3. **노후화:** 직접 훈련한 소규모 커스텀 모델이 3개월 뒤 새로 출시된 범용 LLM API보다 성능이 크게 떨어지는 뼈아픈 현상이 발생합니다.

### 🚀 Product-First 프로토타이핑 전략
현대 AI 엔지니어링은 **일단 가장 비싸고 똑똑한 상용 모델(예: GPT-4, Claude 3 Opus)의 API를 사용하여 최단 시간 내에 프로토타입을 구축**합니다.
1. **아이디어 즉각 검증:** 프롬프트 엔지니어링만으로 MVP(Minimum Viable Product)를 만들어 실제 사용자 피드백을 받습니다.
2. **실제 유저 데이터 수집:** 사용자들이 MVP를 사용하면서 발생하는 살아있는 데이터와 대화 기록을 수집합니다.
3. **점진적 내재화 (Optional):** 서비스가 성공하고 API 비용이 감당하기 힘들 정도로 커지면, 그때 가서 수집된 실제 유저 데이터를 바탕으로 더 작고 저렴한 오픈소스 모델(예: Llama 3 8B)을 파인튜닝(Fine-tuning)하여 내재화합니다.

---

## 3. 요약: AI 엔지니어의 새로운 역할
현대의 AI 엔지니어는 더 이상 '모델을 깎는 장인'이 아닙니다. 대신, 뛰어난 인지 능력을 가진 블랙박스(LLM)들을 레고 블록처럼 조립하여 **오류를 제어하고, 환각을 방지하며, 외부 도구(API, DB)와 안전하게 연결하여 거대한 자동화 시스템(Compound AI System)을 설계하는 '시스템 아키텍트'**에 가깝습니다.
